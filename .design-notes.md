# Design notes — pwa-app core (scratch, delete before PR)

Resolves issue #172 §4's three open questions. Written before touching
Phase 1 files; the layer table below is what `workspace/core.yaml`
Phase 1 writes verbatim.

## 1. The shared-file problem (`src/db/schema.ts`)

Precedent checked: `hedgehog-core-full-stack-app/workspace/core.yaml`'s
`schema` layer scope is
`["packages/db/src/schema/{module}/**", "packages/db/src/schema/index.ts"]`
— the barrel file is directly in scope, appended to by each module's own
schema layer, and `packages/db/src/index.ts` (the barrel-of-barrels one
level up) is `export {}` with a comment: "one re-export line per module,
added by that module's own schema layer... keeps packages/db/src/index.ts
itself static after bootstrap."

This is simpler than the generated-aggregator idea and already proven
against `validateCore` and real usage. Adopting the same shape for
`pwa-app` rather than inventing a generated-file mechanism:

- `src/db/tables/{module}.table.ts` — hand-written by the `entity`/
  `feature` generator, one file per module. Exports the table name, the
  Dexie schema string for that table, and the version number it was
  introduced at (an integer literal the generator writes once, at
  generation time — see §2 below for how it picks the number).
- `src/db/schema.ts` — the barrel. Not generated/derived; a normal
  source file each module's `schema` layer *appends one import + one
  spread line to*, the same append-only discipline
  `packages/db/src/index.ts` uses. It folds every table file's exports
  into the single `version(n).stores({})` chain Dexie requires.
- `schema` layer's scope is
  `["src/features/{module}/data/{module}.schema.ts", "src/db/tables/{module}.table.ts", "src/db/schema.ts"]`
  — the barrel is in scope, not excluded from it. This mirrors
  `full-stack-app` exactly and keeps `schema.ts` a normal file `hedgehog
  verify` can check, rather than something regenerated outside the
  scope system (which would be undetectable drift if a module's layer
  forgot to run the regeneration step).

Rejected: a fully generated/derived `schema.ts` regenerated wholesale
by every generator run. It adds a second mechanism (generation-as-a-
side-effect, outside `scope`) where the existing barrel-append pattern
already works and is what this codebase's own sibling core does. Simpler
wins.

## 2. Migration ordering

Each `src/db/tables/{module}.table.ts` file carries its own version
number, written once by the `entity`/`feature` generator at generation
time — not hand-picked by whoever runs the generator. The generator:

1. Reads every existing `src/db/tables/*.table.ts` file's exported
   version number.
2. Assigns `max(existing) + 1` to the new file.
3. Appends the corresponding `.version(n).stores({...})` line to
   `src/db/schema.ts`.

Race condition under module-axis parallelism: two modules' `schema`
layers can run in the same wall-clock window (different tasks, same
layer id, different `{module}`). Each is a **separate task operating on
a disjoint file** (its own `{module}.table.ts`) plus **one shared file**
(`schema.ts`) both tasks append to. This is exactly the same shape
`full-stack-app`'s `packages/db/src/schema/index.ts` already has under
parallel module tasks, and the scheduler does not special-case it: two
tasks with overlapping scope (both list `src/db/schema.ts`) are treated
as conflicting and are not co-scheduled — `hedgehog`'s scheduler
serializes tasks whose scopes intersect. This falls out of the scope
declaration itself, not an extra locking mechanism: because `schema.ts`
is listed in every module's `schema` layer scope, the two modules'
`schema` tasks conflict on that file and run serially, in whichever
order they're claimed. No exclusive layer or aggregator step is needed
— the existing conflict-detection the engine already does for any two
tasks sharing a scoped file is sufficient, exactly as it is for
`full-stack-app`'s barrel today.

`join`'s workspace-wide `exclusive: true` verify (typecheck + build)
remains the final backstop that catches a version collision or a
malformed chain, the same role it plays for `full-stack-app`.

## 3. Does `service` earn its own layer?

Adopting the issue's own proposal: **drop it**. Five layers, not six:

```
schema → repository → hook → screen → join
```

`repository` absorbs whatever domain logic would have lived in
`service` — for a local-first app with no server tier, a repository
method and a thin service method are usually the same code with an
extra hop. Re-added only if a Phase 7 reference build surfaces real
domain logic with nowhere else to live (the issue's own escape hatch).

## Final layer table (verbatim for Phase 1's workspace/core.yaml)

See `workspace/core.yaml` for the actual (verbatim) file — reproduced
here would risk drifting from it. Note the engine's `parseCoreYaml`
(`src/db/core.mjs` in the `hedgehog` repo) only supports **inline**
bracketed scope lists (`scope: ["a", "b"]`), not YAML block-list syntax
— confirmed by running `loadCore()` against this file directly, which
also confirms `validateCore` and `isModuleAxis` both pass.

Module-axis check against `validateCore`: every non-`once`, non-
`exclusive` layer (`schema`, `repository`, `hook`, `screen`) has
`{module}` in every scope glob. `join` is `exclusive: true` with
`scope: ["**"]`, the documented escape hatch. No layer declares
`verify_radius` — every layer's verify command's only path argument is
inside its own scope glob (`join`'s verify has no path argument at all,
being workspace-wide by nature of `exclusive`), so no radius declaration
is needed per `validateCore`'s coverage rule.

`--remote` entities (§12 of the issue): the `schema` layer's scope for a
`--remote` module additionally includes
`supabase/migrations/{module}.sql`, and verify gains a policy check
step. This is a per-module shape variation the generator applies to
*which files a given module's schema task actually touches*, not a
change to the layer table itself — `core.yaml` doesn't need a separate
layer or branch for it, since `scope` is evaluated per compiled task and
a `--remote` module simply has one more file in its instance of the
`schema` glob set (matched by the same `src/db/tables/{module}.table.ts`-
adjacent convention, e.g. the migration file living at a `{module}`-
templated path). No table changes needed here.
